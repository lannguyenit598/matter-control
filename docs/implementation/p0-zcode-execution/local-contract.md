## 1. Identity and session (local ZITADEL profile)

- Provider: ZITADEL self-hosted local (PO-selected, `local-identity-approval.json`). One canonical issuer, pinned after provisioning into `ops/p0-local/runtime/issuer.txt` and referenced by both stacks via config — never derived from container DNS guesses. All published ports loopback-only.
- Flow: OAuth2/OIDC **Authorization Code + PKCE S256** with `state` and `nonce`; scopes `openid profile email offline_access` + MatterControl API audience.
- **Token storage model (explicit):** access/refresh/ID tokens are held **only in a server-side BFF session store** — an in-process, task-owned store keyed by an opaque, cryptographically random session handle (local profile; production store technology is PENDING-architecture and stays swappable behind one interface). The browser cookie (`__Host-mc_session`, HttpOnly, Secure, SameSite=Lax) carries **only that opaque handle** — never an OAuth token payload, never identity claims. An encrypted JWE wrapper MAY encapsulate the handle for tamper-evidence; that is wrapping of the handle, not token storage in the cookie. Negative tests required: cookie payload must not contain access/refresh/ID token strings or claims (token-exposure scan over Set-Cookie and store contents); a forged/unknown handle resolves to no session (fail-closed 401).
- Session lifecycle: **logout** destroys the server-side session (handle invalid immediately; best-effort RFC 7009 revoke at the issuer) ; **expiry** = server-side TTL (local default 8h idle / 24h absolute, test-configured) after which the handle is refused; **restart** = the local in-process store does not survive a BFF restart — sessions are lost and users re-authenticate (documented local limitation; a durable store is a production-swappable choice, not silently adopted). CSRF: double-submit token on auth-mutating routes + `state` binding. The loopback-HTTP dev exception is documented in `ops/p0-local/README.md` and confined to local config — production keeps Secure and is unselected. No localStorage tokens, no shared API token, no anonymous REST, no password grant, no client-provided actor.
- **Access-token verification: authenticated introspection.** Go product API verifies every bearer token by calling ZITADEL's introspection endpoint with a dedicated API application's private-key JWT client assertion (ZITADEL documented method). Exact checks, fail-closed: `active == true`; `iss ==` pinned issuer; `aud` contains the pinned MatterControl API audience; `exp` > now (60s leeway); `sub` present and non-empty; username/email claims optional and not trusted for authorization. Verifier unavailable/timeout → `port.ErrUnavailable` → 503 `unavailable` problem (never 401, never fail-open). Invalid/inactive → 401 `unauthenticated`. Opaque tokens are never parsed as JWTs; ID tokens are never API bearers. Introspection cache: per-token result cached ≤30s keyed by token hash — explicitly documented as **not** a revocation guarantee; membership/role checks always re-run in the transaction/read path.
- **Identity mapping:** `(iss, sub)` → `users.id` lookup only (existing unique index). **Provisioning is explicit, never implicit**: unknown identity → 403 with the standard uniform body (no auto-create). Local provisioning happens through the task-owned bootstrap script (test users into the product DB); production provisioning is PENDING-PO (admin surface not in P0 scope). Product roles/memberships/verifier designation live in MatterControl tables; ZITADEL org/project/role grants are never consulted for product authorization.
- Logout semantics (tested distinctions): BFF session destroy (always), product membership revocation (authoritative for API access, effective immediately on next transaction/read), issuer token revocation (best-effort RFC 7009 revoke call; introspection cache ≤30s means instant-revocation is not claimed).

### 2.2 Implemented W1 wire details (revision 5)

Additional reads: `GET /workspaces` (landing after login; no other route lists workspace ids), `GET /workspaces/{id}/members` (Workspace OWNER only; member: 403, non-member: uniform 404) and `GET /matters/{id}/members` (any ACTIVE matter member; only ACTIVE rows are listed). `GET /matters/{id}` returns the header, `callerRole` and the `MC-As-Of` read instant.

- **Headers.** Creation commands require `Idempotency-Key` (UUIDv7; absent: 400 `urn:mc:bad-request`). Reads carry `MC-As-Of` when the snapshot instant exists and `MC-Source-Revision`; they are never inside the hashed body. Replays add `Idempotent-Replayed: true` and return the stored bytes. Creations return `201` + `Location` + `ETag`.
- **If-Match → revision.** `If-Match` must be exactly one strong entity tag (weak tags, `*` and lists: 400). The boundary reads the target's current representation as the caller: an equal tag maps to the current revision, any other tag to a stale revision (412). A resource the caller cannot read maps to a nonzero placeholder so the service returns its uniform denial before any precondition outcome. The in-transaction revision check stays authoritative, so a change between the read and the command is still a 412. Absent header: 428 on fresh CAS-scoped writes; replay of a stored outcome never re-checks CAS; scope-none endpoints reject the header (400 `precondition-not-applicable`).
- **Page envelope.** `{ "items": [...], "page": { "limit", "maxLimit": 200, "total", "nextCursor" } }`; the limit is 1..200 (anything else: 400); cursors are opaque base64url. `total` is present only where the store computes it (accessible matters, members).
- **Problems.** `application/problem+json`, `type` = `urn:mc:<code>`, `retryable` hint: `unauthenticated` 401; `forbidden` 403 (also an unprovisioned identity); `last-owner` 403; `not-found` 404; `malformed-body`/`bad-request`/`precondition-not-applicable` 400; `unsupported-media-type` 415; `idempotency-key-reuse`/`idempotency-key-expired`/`validation` 422; `precondition-required` 428; `precondition-failed` 412; `boundary-due`/`outcome-unknown`/`unavailable` 503 (`outcome-unknown` states that no rollback is asserted and is not retryable with a new key).
- **Reconciliation** (`POST /matters/{id}/operations/{key}/reconciliation`) returns the caller's stored receipt when it represents the named matter; otherwise the uniform 404. It never fabricates success.
- **History** includes every command event (`matter.created`, `membership.granted|revoked`, `requirement.created`) in one contiguous per-matter sequence.

Workstream/party/milestone creations are likewise non-receipted (a blind resend could duplicate), so the UI treats their unknown outcome as re-read-only.
- **Derived state is never accepted from a client.** Dependency, timing, attention, critical-chain, milestone readiness are computed per read at the snapshot instant `MC-As-Of`. A patch/transition body with such a member is rejected as an unknown field (400).
- **Dependency semantics (RULE-003):** an edge is satisfied only when its upstream is READY and COMPLETED and, for a `PROOF` gate, VERIFIED; cancelled never satisfies. Self-edges, duplicates, cross-matter links and cycles are refused before saving; the matter row lock serializes racing edge changes so opposing edges cannot both commit. Each derived change bumps the item revision and writes a causal `work.dependency_changed` event (with `cause_seq`); a refresh that changes nothing writes nothing.

Nothing was mutated and no success event exists.

### 2.4 Documents and proof (W3, revision 7)

Verification is **derived**, never set: a subject's state is recomputed from its criteria, claims, assessments, disputes, applicability, proof epoch and the instant (precedence DISPUTED > NOT_REQUIRED > VERIFIED > PARTIALLY_VERIFIED > UNVERIFIED; no criteria is UNVERIFIED, never vacuously VERIFIED). Every write below ends by recomputing the matter's verification and dependency state in the same transaction (`work.verification_changed` / `work.dependency_changed` carry the causing event). Reads use the same evaluation at `MC-As-Of`, so an expiry takes effect at its instant. A criterion claim pins the criterion revision; an assessment pins the subject proof epoch and the exact version assessed.

| Route | Receipt / CAS | Roles | Notes |
|---|---|---|---|
| `GET /matters/{id}/documents` | read | any member | page envelope; each row carries `etag` |
| `POST /matters/{id}/documents` | **receipted** | EDITOR+ | `{name}` → 201 `{id,kind,seq}` |
| `GET /matters/{id}/documents/{docId}[?promoteTo=versionId]` | read | any member | `ETag` = hash of the canonical `document` member; `promotionImpact{invalidatedCriteria,unaffectedCriteria,token}` when `promoteTo` is given |

### 2.5 Regulatory filings (W4, revision 8)

MatterControl records what is known about a filing; it files nothing (RULE-012). A filing is an ACTION work item (`proofRequired` chosen at creation) plus a filing record: the linked Requirement (the obligation; never auto-completed or auto-verified by approval), the authority external party, the stage, cycles, immutable submissions and append-only observations. **The filing item's ETag is the CAS token of every stage command and moves on each of them** (a stage change that leaves the execution unchanged still bumps the revision). The generic status endpoint refuses a filing (`409 rejected / managed-by-filing`): execution follows the stage.

| Route | Receipt / CAS | Roles | Notes |
|---|---|---|---|
| `GET /matters/{id}/filings`, `GET …/filings/{filingId}` | read | any member | detail carries `filing`, `cycles`, `submissions`, `observations`, `next` (stages reachable) and the item envelope (`etag`) |
| `POST /matters/{id}/filings` | **receipted** | EDITOR+ | `{title, outcome, requirementId, authorityPartyId, ownerId?, proofRequired}`; the Requirement and the authority must belong to the matter |
| `POST …/filings/{filingId}/stage` | CAS (item ETag) | EDITOR+ | `{to, reference?, observedAt?, evidenceIds?, versionIds?, externalRefs?, requestRef?, cycleOwnerId?, cycleDue?, reason?}` |
| `POST …/filings/{filingId}/negative-outcome` | CAS | EDITOR+ | `{outcome REJECTED/WITHDRAWN, evidenceIds, reference?, observedAt?}`; the stage never changes; attention is raised (`NEGATIVE_FILING_OUTCOME`) |
| `POST …/filings/{filingId}/closure`, `…/reopening` | CAS | OWNER | `{reason}`; closure cancels a filing with an unresolved negative outcome; reopening a completed/cancelled filing advances the proof epoch (when proof is required), resolves the negative outcome and keeps all history |

Stage machine (every other ordered pair is `transition-not-allowed`): REQUIREMENT → PACKAGE_PREPARATION → SIGNATURE → SUBMISSION → RECEIPT → AUTHORITY_REVIEW → {SUPPLEMENT → RESPONSE → AUTHORITY_REVIEW}* → APPROVAL (also RESPONSE → APPROVAL); an approved filing that an owner reopened may be approved again (APPROVAL → APPROVAL).

Guards and execution coupling (same transaction as the observation): PACKAGE needs an owner and, when proof is required, declared criteria (`package-criteria-required`) → IN_PROGRESS; SIGNATURE needs identified versions/references (`package-contents-required`); SUBMISSION and RESPONSE need every mandatory criterion currently satisfied (`guard-failed`, message lists the criteria and why — an owner's reasoned criterion retirement is how a signature stops applying), a reference, exact version ids that exist in the matter, an observation time not in the future; they create the cycle's immutable submission; SUBMISSION → WAITING on the authority ("acknowledgement outstanding"); RECEIPT needs existing, non-withdrawn acknowledgement evidence; AUTHORITY_REVIEW → WAITING on the authority; SUPPLEMENT needs the authority's request reference, an owner and a due date and opens cycle n+1 (cycles count authority rounds; proof epochs count reopenings; they are independent); APPROVAL needs outcome evidence recorded after the latest reopen (`evidence-before-reopen`), is refused while a negative outcome stands (`negative-outcome-open`) and completes the filing. Other codes: `filing-closed`, `owner-required`, `reference-required`, `evidence-required`, `unknown-evidence`, `unknown-version`, `observed-in-future`, `supplement-details-required`, `not-submitted`, `invalid-outcome`, `no-negative-outcome`, `not-closed`, `correct-the-original`, `nothing-to-correct`, `unknown-requirement`, `unknown-party`.

Unknown-outcome recovery: creation may be resent with the same key; every stage command is revision-guarded and is **re-read, never resent** (the append-only observations show what was recorded).

Local boundary: for filings without proof epochs (`proofRequired=false`) "evidence after the reopen" is bounded by the recorded reopen observation.

## 3. DTO, decode, fingerprint, error and replay semantics

- **DTO presence policy:** every field explicitly typed; server-owned fields (revision, seq, recordedAt, states) are always present; `owner`, `dueAt`, `workstreamId`, `applicabilityReason` are `null` until set — client renders explicit "—"/unassigned, never invents values. Producer ownership: only the command that owns a field writes it; read models never merge unrelated sources.
- **Strict decode:** JSON bodies decoded with disallowed-unknown-fields and duplicate-key rejection → 400 `malformed-body`. No caller-supplied actor/RequestHash/derived-state fields accepted anywhere (rejected as unknown fields).
- **Fingerprint (intent hash):** SHA-256 over the deterministic framed tuple from BE02 prep §4 (`version/method/routeTemplate/path/body/preconditions`), fixed member order, no normalization, exact strings, precondition scopes per endpoint CAS table. Bound to idempotency key as replay input; never trusted from client.
- **Error precedence (amended in revision 5):** unauthenticated 401 (authentication runs first, so no body is read for an unauthenticated caller) → decode 400 → forbidden 403 (uniform body, no resource leak) → not-found 404 (fixed body, indistinguishable classes) → key reuse/expired 422 → boundary-due 503 `boundary-due` → unavailable/deadline 503 `unavailable` → outcome-unknown 503 `outcome-unknown` (body states explicitly that no rollback is asserted; never auto-resubmit) → unexpected 500 fixed body. Problem types: `about:blank` replaced by product problem URNs `urn:mc:<code>` with stable titles; native User API bytes unchanged (BG-02 scope split). Retry convention (which 5xx are retryable with same key): PENDING-PO via INT-D09; implemented as documented per-problem `retryable` hint field pending that decision.
- **Replay/stable wire:** receipt stores the immutable created-result snapshot (BE01 pattern). Replay returns the versioned stored snapshot byte-stably (per read snapshot for outer metadata; nested committed outcome unchanged); `Idempotent-Replayed: true` header on replay; Location/ETag recomputed from stored snapshot deterministically. Own-key lookup requires saved-workspace + every represented-matter current read access (BE01 rule preserved) before disclosure.
- **Revision preconditions:** `If-Match: "<revision>"`? No — If-Match carries the strong ETag; server maps ETag→revision via the deterministic representation rule in §4 and validates inside the command transaction (`expected_revisions` in the framed tuple). Mismatch → 412 `precondition-failed`. Missing If-Match on CAS-scoped writes → 428 `precondition-required`.

## 4. Representation/ETag/CAS (BG-08 resolution — implementation choice pending review)

Chosen mechanism: **(a)-style stable resource representation + header-carried per-read provenance.**

- Resource bodies contain only revision-determined fields (identity/title/outcome/states/epochs/owner/due/workstream/revision). Per-read provenance (`MC-As-Of` snapshot time, `MC-Source-Revision`, later `MC-History-Materialized-Through`) is returned as response headers, never inside the hashed body.
- `ETag: "<sha256-hex>"` = SHA-256 of the exact body bytes (canonical JSON encoding, fixed key order). Equal ETags imply equal bytes by construction; a new revision ⇒ new body ⇒ new ETag. If-Match is validated by revision equality inside the transaction (the ETag↔revision binding is deterministic because bodies are revision-determined), never by byte comparison.
- **Time-derived members (revision 6):** where a resource has members that move with the clock (a work item's `derived.timing` / `derived.attention`), the response nests the revision-determined part as `item` and the strong ETag is the SHA-256 of the canonical bytes of `item` alone. Equal ETags imply equal `item` bytes; a clock change can never invalidate a valid If-Match. If-Match is still validated by revision equality inside the transaction.
- Temporal fence (BG-06): derived states are computed only by the owning command transaction; reads report the snapshot `asOf` truthfully in headers and never fabricate `historyMaterializedThrough`. Where a true temporal evaluation is not implemented, the field is absent, not defaulted.

## 5. Next Action (N1) normative home and F-08/F-10 read grain

- **N1:** Next Action / My Actions / Waiting On / readiness aggregates are computed **server-side in core services** (single canonical implementation); FE renders results verbatim. No client-side recomputation.
- **F-08 evidence-gap classifier (adopted as implementation mapping of the OWNER_TECHNICALLY_CONFIRMED candidate; formal architecture adoption is PENDING-Claude):** per requirement/proof-criterion, ordered classification S0 satisfied-suppression (current-epoch verified/withdrawn-by-supersede) → S1 MISSING (no evidence) → S2 first-match by severity order WITHDRAWN > DISPUTED > REJECTED > EXPIRED > PENDING_REVIEW; epoch-scoped (old-epoch-only findings → PENDING_REVIEW residual). Gap enum is display vocabulary, not the claim catalogue; no F-07 claim.status revival.
- **F-10 filing/cycle read grain (same status):** bounded read via 3 relation routes (matter→filings, filing→cycles, cycle→observations), totals-only for cycle item counts, cursor tuples of distinct `(recorded_at, seq)` per route — no hidden caps; nested version references bounded per adopted Option B shape. Dispositions DISPUTED etc. remain on their own axes.
- Business clock: effective_at ≤ recorded_at enforced (schema); boundary evaluation inside command transactions only; no wall-clock substitution.

## 6. Concurrency, versions, epochs, object boundary

- All mutations take `FOR UPDATE` matter lock and bump matter revision in the same transaction (BE01 pattern); expected-revision preconditions per §2 CAS column; lost-update → 412 with current revision in problem extensions.
- Proof epochs: reopen/dependency-reblock that invalidates proof opens epoch n+1 (`proof_epoch_opened_at` recorded); proof rows carry the epoch they were accepted in; verification of a superseded epoch is refused.
- **Local object boundary (W3):** new core port `ObjectStore` (Put/Get/Delete with scoped paths) + local filesystem adapter under `ops/p0-local/data/objects/` (task-owned, 0700); documents/versions store content-addressed object refs + metadata in product DB; retrieval only through authorized product endpoints (bytes streamed after membership recheck); no unsigned links, no cloud provider (production provider PENDING-PO). Upload/read limits: locally configured test values (declared in `ops/p0-local/README.md`), no production commitment.
- Import/export (W6): formulas never executed; CSV/XLSX parsed as data only; export rechecks rights at retrieval.
