## Stable residual findings (MC-002-INTA-FE-R2-F01…)

**R2-F01 — P0, pre-upstream blocker — phase lifecycle is causally unexecutable: no stage barriers, no read between restarts, no phase-order enforcement.**
`path: src/driver.ts:runPhase case1/case2/case4`. Concrete: (1) phase1 prints "ZCode restart Go (INT-PERS-01) **then** Codex stop/restart PG (INT-PERS-02). Run phase 2" — phase2 then dispatches `INT-PERS-01` and `INT-PERS-02` back-to-back, so the PERS-01 GET runs *after the PG restart too*; the "state after Go restart only" attribution the frozen matrix §D requires cannot be established. (2) phase4 prints "Codex restart PG … Then ZCode stop Go", then in the same synchronous function immediately dispatches `INT-PERS-03`, `INT-PERS-04`, `T12` — impossible without an operator race; async dispatch doesn't wait for lifecycle completion, and there is no persisted confirmation that any restart/stop happened (checkpoint stores no phase-entry confirmation). (3) No phase-order gate: `runPhase(3)` and `runPhase(4)` require only `checkpointA` existing — phase4 may run directly after phase1, skipping T9/W9/T10, and any later phase re-runs are stopped only by the ledger, not by order. Per the original contract the barrier lives in the driver only: an explicit manual stage command or persisted confirmation file (recorded by the operator's own return evidence) gated before each restart-dependent substep group, plus a phase-sequence check (previous phase recorded completed) is the minimum. No frontend Go/Docker lifecycle actions — the prompts alone are not barriers.
**Regression:** fake-fetch phase tests asserting (a) phase2 refuses while phase-entry confirmation for PERS-01 window absent; (b) PERS-01 read recordable between the Go and PG stage confirmations; (c) phase4 refuses without phase3 completion marker; (d) out-of-order invocation is refused with zero dispatches.

**R2-F02 — P0, pre-upstream blocker — write-once ledger enforced only *after* dispatch: rerun can replay a mutation upstream (including X).**
`path: src/driver.ts:runPhase (all cases); persistEnvelope`. Concrete: every phase step does `dispatchCaseToHarness` first, then `persistEnvelope`. If the process crashes (or dispatch fails) after the harness executed upstream but before the driver ledger write, a rerun re-dispatches. Worse, the normal rerun path: `persistEnvelope` byte-equal idempotency is checked only against a ledger that hasn't recorded reruns yet — a re-run of phase3 dispatches the T9 PATCH upstream unconditionally, mutates nothing detectable, then throws "already executed with different content" *after the write already occurred* (new requestId/timestamp makes the envelope differ). Same for T1 and T11c's one-shot X POST: "never autoretry/probe X unknown" is violated on any rerun. There is no durable attempt-started intent before I/O and no before-dispatch phase-order gate. Not a receipt/product-idempotency feature demand — the minimal fix is harness-local: before any dispatch, read a one-shot per-case substep guard (e.g. `.run-state/substeps/<runId>/<caseId>.started` append-only); refuse re-dispatch if it exists without a completion record; write `started` before the dispatch and `completed` only after `persistEnvelope`. Corrupt/garbage guard state must fail closed. No automatic retries; unknown-X never re-POSTed, no new key, no list/SQL probe.
**Regression:** fake-fetch count test: rerun of phase3 with completed ledger performs **zero** dispatches; simulated crash-after-upstream-write-cause → rerun refuses; phase1 fresh run dispatch counts exactly 11/2/3/7 respectively.

**R2-F03 — P1 — preflight refuses the *correctly provisioned* environment: run cannot start after Codex does its job.**
`path: src/driver.ts:assertNoRunIdCollision`. Concrete: (a) the evidence-directory check runs even with `allowResume=true` — it always throws on any existing `/tmp/mc002-inta-evidence/*/<runId>` dir; (b) the Docker check `execSync("docker ps -a --filter name=mc002-inta-pg-<runId>")` always throws on the container the contract *requires Codex to create before phase1* — the driver cannot run against the verified owned ENV; this also puts a general Docker-controller dependency in frontend code the frozen scope does not grant. The actual workflow needs bounded provenance: same-runId owned assets (this run's reserved container/evidence) must not conflict with a resume of the same run; foreign runId collisions must be refused; the driver should record — not query — external resources (container ownership/verify is Codex's gate). (c) Minor fail-open rider: in the `!allowResume` counters preflight, `JSON.parse` errors from `counters.json` are swallowed unless they match "RunId collision refused", so a corrupt counters file silently passes collision preflight even though `RequestIdGenerator` would later fail closed — align preflight with the fail-closed read.
**Regression:** preflight with existing owned-per-runId container/evidence + `resume`/acknowledged-ownership mode → proceeds; foreign runId asset → refuses; corrupt counters during preflight → refuses.
