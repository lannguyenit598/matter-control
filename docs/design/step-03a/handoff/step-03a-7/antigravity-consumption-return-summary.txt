## 2. Reconciled Control Room Architecture (8 Server Sections + 2 Embedded Groups)

```
+----------------------------------------------------------------------------------------------------+
| CONTROL ROOM SERVER SNAPSHOT (One asOf, One sourceRevision, One historyMaterializedThrough)         |
+----------------------------------------------------------------------------------------------------+
| 1. condition:    { matterRef, label, completeness: COMPLETE|INCOMPLETE, exceptions: [{code,count}]} |
| 2. blockers:     [ Upstream Cause Cards (rootCause: bool, axes, waitRef, failingGates) ]            |
| 3. nextActions:  [ Action Cards (RULE-021 rank) ] + excluded: [{ref, reason: WAITING|BLOCKED|...}] |
| 4. waitingOn:    [ Wait Cards (partyRef|condition, internalOwnerRef, openedAt, openedEventSeq) ]    |
| 5. milestones:   [ Milestone Cards (readiness: READY|NOT_READY|UNASSESSED, satisfied, total) ]     |
| 6. evidenceGaps: [ Gap Cards (MISSING|PENDING_REVIEW|REJECTED|EXPIRED|DISPUTED|WITHDRAWN) ]         |
| 7. decisions:    [ Open Decision Cards (label: question, lifecycle, relatedRefs) ]                  |
| 8. recentChanges:[ Chronological Audit Events (seq descending, targetRef, correlationId) ]          |
+----------------------------------------------------------------------------------------------------+
| Embedded in every card: [CRI-09 Actionability (permittedActions?)] + [CRI-10 Navigation (ref, relatedRefs)] |
+----------------------------------------------------------------------------------------------------+
```

1. **Single Snapshot Boundaries**:
   `GET /api/v1/matters/{matterId}/control-room` returns a single `REPEATABLE READ READ ONLY` projection sharing `meta.asOf`, `meta.sourceRevision`, and `meta.historyMaterializedThrough`. The client never stitches together legal truth from independent section queries.
2. **Server Availability (`AVAILABLE` vs. `UNAVAILABLE`)**:
   - `AVAILABLE + []` = **True Zero** (authorized, successfully evaluated empty set).
   - `UNAVAILABLE + null` = **Evaluation Failure** (never rendered as zero or ready). Renders a section error container.
   - Root returns HTTP `200 OK` when at least one section is `AVAILABLE`; returns HTTP `503 Service Unavailable` (`/problems/unavailable`) when the snapshot cannot open or all sections fail.
   - `condition.completeness` displays `INCOMPLETE` if any contributing section is `UNAVAILABLE`. Exception counts sourced from an unavailable section are `count: null` (rendered as "Unknown", never `0`).
3. **Client-Owned `STALE` State**:
   `STALE` is client-managed. When background polling fails, the client retains the prior authorized response, tags the view `STALE`, and renders it with its **original `asOf` timestamp**. It is never presented as current truth.
4. **Immediate Revocation Purge**:
   HTTP `401` or uniform `404 /problems/not-found` (returned identically for non-members and missing matters) forces the client to **immediately purge all cached matter detail and memory**.
5. **Upstream Blocker Causes**:
   Blocker cards represent **unsatisfied upstream causes**, displaying the cause's own WAITING/READY axes and `waitRef`. `rootCause: true` is highlighted prominently (e.g., Atlas T0 RQ-04 WAITING · READY failing DEP-01). Downstream targets are reached via DR-06.
6. **Next Actions & Atlas T0 Exclusions**:
   Requirements **never** enter `nextActions`. When candidate actions are empty at Atlas T0, the section carries `excluded: [{ref, reason: WAITING|BLOCKED|UNASSIGNED}]`, which the client renders via [`EmptyState`](file:///tmp/mattercontrol-step02-frontend/src/components/molecules/empty-state.tsx#L1-L43) without inventing tasks.
7. **Embedded Actionability & Navigation**:
   - `permittedActions` is an advisory hint. When absent, actions are treated as unknown, offered safely, and subject to backend command authorization; no permission is inferred. `viewerRole` drives UI affordances only.
   - All navigation uses typed `{kind, id}` references from a closed 25-kind enum; no raw URLs or harness IDs.

## 3. Detail Read Catalogue (DR-01..17), 30 Operations & Material Route Gaps

All 17 DR capabilities and 30 read operations were reconciled against frontend consumption patterns. We identified **two material gaps** and **one clarification** regarding the 4 replaced detail routes:

```
+---------------------------------------------------------------------------------------------------------+
| REPLACED ROUTE EVALUATION & MATERIAL GAPS                                                               |
+---------------------------------------------------------------------------------------------------------+
| DR-02: /workstreams/{id} rejected  --> List /workstreams + Grid filter. Small list (<=200). Safe.      |
| DR-03: /milestones/{id} rejected    --> Extended /milestones/{id}/readiness point lookup. Safe.         |
| DR-08: /evidence/{id}/claims rej.  --> Claims inline in /evidence/{id}. GAP on orphan claimRef.        |
| DR-13: /external-parties/{id} rej. --> List /external-parties (paginated). MATERIAL GAP on party lookup.|
+---------------------------------------------------------------------------------------------------------+
```

### Material Gaps & Targeted Questions for Claude Code:

1. **Material Gap 1 (DR-13 — `EXTERNAL_PARTY` Reference Resolution Across Pagination)**:
   - *Observation*: Proposed `GET /external-parties/{id}` was rejected in favor of collection `GET /api/v1/matters/{matterId}/external-parties` (keyset paginated: `after`, `limit <= 200`) and `GET /api/v1/matters/{matterId}/waits?partyId={id}`.
   - *Failure Mode*: In large corporate transactions with $> 200$ external parties (syndicate lenders, local counsel, regulatory contacts), clicking `{kind: "EXTERNAL_PARTY", id: "ep-999"}` from a wait or filing card cannot resolve the party's label, contact info, or `inactive` flag if it resides on page 2+. Keyset cursors cannot jump to an arbitrary ID without $O(N)$ sequential page fetches, and no `?id=` filter is defined on the collection.
   - **Smallest Concrete Question for Claude**:
     > *"For DR-13, when resolving a clicked `EXTERNAL_PARTY` reference `{kind: 'EXTERNAL_PARTY', id}` across a paginated collection, should `GET /api/v1/matters/{matterId}/external-parties` support an `id` query filter (`?id={id}`) returning a 1-item page, or should point-lookup `GET /api/v1/external-parties/{id}` be reinstated to avoid client-side sequential cursor traversal?"*

2. **Material Gap 2 (DR-08 — Orphan `EVIDENCE_CLAIM` Reference Resolution)**:
   - *Observation*: Proposed `GET /evidence/{id}/claims` was rejected; claims are provided inline inside `GET /api/v1/evidence/{id}` as `claims[]`. The catalogue provides `GET /api/v1/evidence-claims/{id}/assessments` (DR-09).
   - *Failure Mode*: `EVIDENCE_CLAIM` is an explicit member of the 25 typed reference kinds. If an audit log (`recentChanges`), dispute record, or assessment history cites `{kind: "EVIDENCE_CLAIM", id: "claim-456"}` without an explicit parent `evidenceRef`, the frontend cannot resolve the claim entity. `GET /api/v1/evidence/{id}` requires an `evidenceId`, not a `claimId`, and DR-09 returns assessment history, not the claim entity definition.
   - **Smallest Concrete Question for Claude**:
     > *"Does every reference of kind `EVIDENCE_CLAIM` contractually guarantee the presence of its parent `evidenceRef`, or does `GET /api/v1/evidence-claims/{id}/assessments` return the parent claim definition inline to prevent unresolvable orphan claim references?"*

3. **Clarification 3 (DR-02 — Workstream Collection Boundedness)**:
   - *Observation*: Workstream member navigation via `grid?workstreamId={id}` is safe. However, looking up a workstream's label from an ID requires querying `/workstreams`.
   - **Smallest Concrete Question for Claude**:
     > *"Is `GET /api/v1/matters/{matterId}/workstreams` contractually guaranteed to be bounded ($\le 200$ items) and unpaginated per Matter so clients can safely cache all workstream labels in a single read?"*

4. **DR-03 (Milestones — Verified Safe)**:
   - Extending `GET /api/v1/milestones/{id}/readiness` with `label`, `dueAt`, and `critical` provides a direct, unpaginated point lookup by ID, completely avoiding collection pagination issues.

## 5. Candidate Tests (CT-01..22) & OpenCode Testability

All 22 Candidate Test rows (CT-01..22) remain **`NOT_RUN`**. The 8 testability questions formulated by Claude Code were evaluated from a frontend consumption perspective and confirmed to be **100% testable**:
- **Q1 (Uniform 404)**: Client renders identical `UniformNotFoundState` on 404 across both non-existent matters and unauthorized matters, ensuring zero information leakage.
- **Q2 (Fault-injected partial 200)**: Consumer renders the section error container while other sections remain interactive; `condition.completeness` displays `INCOMPLETE`.

- **Q4 (Keyset cursor reachability)**: Consumer passes cursor strings as opaque parameters without parsing; validates that pagination can traverse all matching records.
- **Q5 (Filing submitted version ref)**: Consumer navigates to the exact `submittedVersionRef` linked in the filing cycle, proving it does not default to the document's `currentVersion`.
- **Q6 (Atlas T0 exclusion rendering)**: Consumer renders the empty Next Actions queue with explicit excluded reasons (`WAITING`, `BLOCKED`, `UNASSIGNED`) and surfaces RQ-04 as the top root cause blocker.
- **Q7 (Read side-effect freedom)**: Inspecting event sequence counters before and after read operations confirms that read consumption creates zero domain events.
- **Q8 (Kind-mismatched ID 404)**: Passing an Action ID to a Requirement route returns 404, which the client handles gracefully via its standard not-found component.
