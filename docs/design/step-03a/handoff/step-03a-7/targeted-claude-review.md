## 3. TQ-02 — Control Room read decisions

### Information groups
All 10 groups are P0 and are traced to approved requirements, with no percentage or invented metric. They need not be 10 panels:
- **Server sections (8):** condition, blockers, nextActions, waitingOn, milestones, evidenceGaps, decisions, recentChanges.
- **Embedded in every card (2):** CRI-09 actionability and CRI-10 navigation.

Each section has an approved trace, a server order, a card shape and a continuation route (JSON `control_room.sections`). The semantic invariants hold:
- Requirement ≠ Action: Requirements never appear in nextActions.
- Criterion ≠ Evidence: a gap carries no fabricated Evidence reference.
- COMPLETED ≠ VERIFIED: shown as separate axes, with exception code COMPLETED_UNVERIFIED.
- WAITING ≠ BLOCKED: the waitingOn and blockers sections are separate, and a subject's dependency state comes from its own axes.

**Blockers are causes, not blocked targets.** Each blockers card is an unsatisfied upstream cause: a node with at least one failing outgoing gate. It carries the cause's own axes and wait (`waitRef`), `failingGates`, and a `rootCause` flag, which is true when the cause itself is dependency READY.
- Order: critical-unsatisfied first (dependency-engine §5), then root causes, then due, then id.
- Example: at AtlasT0, RQ-04 (WAITING · READY, failing DEP-01) is the top root-cause card. AC-05/07/08 follow as intermediate causes.
- Why: a "nodes that are BLOCKED" list would never show RQ-04, which breaks CRI-02, E-01 and the AC-137 "top blocker" task.
- Blocked targets and transitive impact come from DR-06.
- Exact proof, version, claim and cycle identity is kept.
- Event History is untouched by reads.

### READ-01 — server-assembled projection in one snapshot (decided)
The Control Room uses the existing candidate route `GET /api/v1/matters/{matterId}/control-room`. It is a display projection evaluated in one ADR-002 §1.6 REPEATABLE READ READ ONLY snapshot, with no persisted entity, store, cache, realtime channel or pipeline.

Why one snapshot:
- FR-009 Validation requires that the "summary ties to same scope/as-of".
- AC-109 requires a match "at that boundary".
- Client composition of many reads would produce mixed snapshots and repeat authorization per call.

Detail stays lazy through typed reads.

### READ-02 — freshness, partial failure, bounds (decided)

**Freshness**
- One `meta.asOf` and `meta.sourceRevision` apply to every AVAILABLE section. Per-section asOf/sourceRevision are removed.
- Section availability is **AVAILABLE | UNAVAILABLE** only.
- **STALE is not a server value.** No retained-data store is selected anywhere, so STALE can only be the client's label on a previously received response kept after a failed refetch, shown with that response's asOf.

**Partial failure**
- The root returns 200 when at least one section is AVAILABLE.
- It returns 503 `/problems/unavailable` when the snapshot cannot open or no section is available.
- A 200 never means every section is available.
- AVAILABLE + `[]` means a successful zero. UNAVAILABLE + `null` means evaluation failed, never zero or READY.
- `condition.completeness = INCOMPLETE` whenever a contributing section is UNAVAILABLE. Each exception count sourced from that section is `null`, never 0 (FR-009: "do not display zero blockers from failure").
- A milestone UNASSESSED result and an empty nextActions list are successful results. nextActions always carries `excluded[]` reasons (WAITING / BLOCKED / UNASSIGNED, per dependency-engine §7), which is what renders AtlasT0.

**Bounds and continuation**
- Every section is bounded, server-ordered, and has `nextCursor` pointing to a named collection route. That cursor belongs to the continuation route, and the route's default order for the filter equals the section order, so continuation reaches every row. Each continuation collection states its default order in the JSON.
- Continuation pages are new snapshots. Each carries its own asOf/sourceRevision and is never silently merged as coherent.
- In-Matter `total` values come from the same snapshot. This is not a fabricated total because P0 has no sub-Matter ACL (permission-matrix). Any future narrower access rule reopens this.
- Page sizes are an implementation parameter under the inherited candidate cap of 200. No new number is set.

### READ-03 — routing, refs, schema, errors (decided)
- **Refs:** typed `{kind, id}` from a closed 25-kind enum that keeps Requirement and Action distinct. `FILING_CYCLE` uses `(filingId, cycleNo)`, reusing candidate `expectedCycleNo`. `EVENT` uses seq. matterId appears only in responses that span Matters.
- **Axes:** reuse the candidate node axis shape.
- **Correlation:** `X-Request-ID` response header, not a body field.
- **Common read rules RC-1..10:**
  - check order is 401 → membership (uniform 404) → 422 → 503, so a revoked caller with a valid cursor gets 404;
  - **no 403 on P0 reads**, because every member may read the whole Matter;
  - other-kind or foreign ids return 404;
  - `private, no-store`, with no If-Match/If-None-Match on GET;
  - cursors are opaque, carry only keyset values the caller could see, and are bound to actor, matter, collection, filter and sort;
  - reads create no domain event; denials go to the restricted security audit.

## 7. Antigravity read-consumption constraints

1. **Section-by-section handling.** A 200 from control-room is not "all fresh". Render each section by its `availability`. UNAVAILABLE + null shows an error region, never zero or READY. Show `condition.completeness = INCOMPLETE` explicitly, and render a `count: null` exception as unknown, never 0.
2. **Blockers.** Blockers cards are causes. Show `rootCause` causes prominently, with their own WAITING/READY axes, and reach the blocked targets through DR-06.
3. **STALE.** STALE is client-owned. Label a retained response as stale with its own asOf after a failed refetch, and never present it as current.
4. **Continuation.** Keep one overview boundary. A continuation or detail response with a newer `sourceRevision` gets a "changed since overview" notice and is not merged silently.
5. **No client-side state.** Never compute axes, readiness, eligibility or exception counts on the client. Display server values and reasons.
6. **Refs.** Resolve a ref only through the route for its kind. Never substitute a document's current version for a `submittedVersionRef` or an `assessedDocumentVersionRef`. A gap without an `evidenceRef` stays a gap.
7. **Not-available state.** Every 404 renders the same "not available" state, with no retained title or count. On 404 after revocation, purge cached detail for that Matter.
8. **Cursors and totals.** Cursors are opaque: do not parse, build or persist them across users. Show `total` only when present.
9. **Actionability.** `permittedActions` is advisory. When it is absent, treat the action as unknown, offer it safely and render the server's command problem; never treat it as permitted. `viewerRole` drives affordances only.
10. **Request mechanics.** No If-Match on GETs, and keep the transport seam (C-API-1 from MC-003A.6). Record `X-Request-ID` for diagnostics, without logging payloads.
