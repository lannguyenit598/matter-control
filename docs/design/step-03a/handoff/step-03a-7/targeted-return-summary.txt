How the Control Room read works (TQ-02)
- One server-built projection, one snapshot. The existing candidate route GET /matters/{m}/control-room is assembled server-side in a single read snapshot. FR-009 requires the "same scope/as-of", AC-109 requires a match at "that boundary", and ADR-002 §1.6 already provides this kind of snapshot. Client-side composition would mix snapshots. No new entity, store or cache is introduced.
- Freshness. One asOf/sourceRevision covers every section. Each section is either AVAILABLE or UNAVAILABLE. STALE is not a server value; it is the client's label on an older response it kept after a failed refetch.
- Partial failure. The root returns 200 if at least one section works and 503 if none do. Empty-but-available ([]) is different from unavailable (null). A condition count drawn from a failed section is null, never 0.
- Paging. Each section's nextCursor works on a named collection route whose default order matches the section. Continuation pages are new snapshots and are never silently merged.
- Refs, errors and caching. References are typed {kind, id} over 25 kinds; filing cycles use (filingId, cycleNo). Check order is 401, then a uniform 404 for non-member or nonexistent, then 422, then 503. P0 reads never return 403. No If-Match on GETs, and responses are private, no-store.
- Sections. Eight are server sections; actionability and navigation are carried on every card.
- Blockers are causes, not blocked targets. A card is any node with at least one failing outgoing gate, flagged rootCause when the node itself is dependency READY. At AtlasT0 this makes RQ-04 (WAITING but READY) the top card. The first draft listed blocked nodes instead, which would have hidden RQ-04; the advisor caught this and I checked it against Atlas §5.
