14: | Idempotency | `Idempotency-Key` (UUIDv7, one per user intent) required on every non-GET. Receipt `(actor, key) → scope (matter or workspace), request hash, status, body` is inserted **only in the command's own transaction**: visible receipt ⇔ committed 2xx; failures leave none. Hash = SHA-256(method, route template, path params incl. scope, canonical body, If-Match/If-None-Match, expectedRevisions). Each receipt also records every Matter represented in its stored body (data-model §6 `command_receipt_matters`; for `POST /workspaces/{ws}/matters`, the created Matter). Replay check runs **after** the scope lock and current authorization: same hash + caller currently has read access to the scope **and** current Matter read access (active workspace + matter membership) to every represented Matter → stored response, `Idempotent-Replayed: true`; any check fails → uniform 404 (stored body never returned; Workspace OWNER grants no Matter access, AC-118); different hash → `422 idempotency-key-reuse`. Same-key duplicates serialize on the scope lock; the second replays, or executes once if the first aborted. Key age is checked inside the transaction at `t_cmd` (after admission, so network or queue delay cannot bypass it): key time older than `receiptRetention − maxCommandDuration − allowedSkew`, or more than `allowedSkew` in the future → `422 idempotency-key-expired`. `purge_after = committed_at + receiptRetention`, so any same-key request that passes this check — including a delayed original — finds a committed receipt if one exists and replays instead of re-executing. Receipts purged only by the retention role after `purge_after` (TB-06). Bulk commit/import confirm use outcome records (§3.6, §3.7) |
15: | Unknown outcome | `GET /api/v1/operations/{idempotencyKey}` (own keys) re-runs current read authorization on the receipt scope and every represented Matter (as for replay) → `200 {status: COMMITTED, response, asOf}`; key past retention → `410 idempotency-key-expired` (reconcile via `GET /matters/{m}/events?commandKey=`); otherwise uniform `404`, meaning only *no committed outcome visible to you as of `asOf`* — **not** "never committed" (it may be in flight, or access lost). 47: 
48: AUTHORITY_REVIEW → SUPPLEMENT opens cycle n+1 with request reference, owner, due, and new package criteria revisions for requested items. RESPONSE records a new `FilingSubmission` in that cycle with exact versions (e.g., v3); cycle 1 submission with v2 remains intact (AC-129). Multiple supplement cycles are unbounded; the latest open cycle's wait is the current "Waiting On".
