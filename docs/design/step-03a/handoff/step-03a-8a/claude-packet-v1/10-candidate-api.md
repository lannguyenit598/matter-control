## 1. Conventions

| Topic | Contract |
|---|---|
| Base | `/api/v1`; JSON only; resources addressed by UUIDv7; matter scope in path `/matters/{matterId}/…` or derived from the resource and validated |
| Authentication | `Authorization: Bearer <user access token>` on every `/api/v1` route; no shared service token for user data (TB-04) |
| Revisions | Every mutable resource returns `revision` and strong `ETag: "<revision>"` (template format). `If-Match` is required **iff** the endpoint's CAS scope in §1.1 names a target (stricter than template, where absent If-Match meant "no precondition"): missing → `428 precondition-required`; mismatch → `412 stale-revision`; sent to a scope-none endpoint → `400 precondition-not-applicable`. Further revisioned inputs go in `expectedRevisions: {id: revision}` exactly where §1.1 requires |
| Idempotency | `Idempotency-Key` (UUIDv7, one per user intent) required on every non-GET. Receipt `(actor, key) → scope (matter or workspace), request hash, status, body` is inserted **only in the command's own transaction**: visible receipt ⇔ committed 2xx; failures leave none. Hash = SHA-256(method, route template, path params incl. scope, canonical body, If-Match/If-None-Match, expectedRevisions). Each receipt also records every Matter represented in its stored body (data-model §6 `command_receipt_matters`; for `POST /workspaces/{ws}/matters`, the created Matter). Replay check runs **after** the scope lock and current authorization: same hash + caller currently has read access to the scope **and** current Matter read access (active workspace + matter membership) to every represented Matter → stored response, `Idempotent-Replayed: true`; any check fails → uniform 404 (stored body never returned; Workspace OWNER grants no Matter access, AC-118); different hash → `422 idempotency-key-reuse`. Same-key duplicates serialize on the scope lock; the second replays, or executes once if the first aborted. Key age is checked inside the transaction at `t_cmd` (after admission, so network or queue delay cannot bypass it): key time older than `receiptRetention − maxCommandDuration − allowedSkew`, or more than `allowedSkew` in the future → `422 idempotency-key-expired`. `purge_after = committed_at + receiptRetention`, so any same-key request that passes this check — including a delayed original — finds a committed receipt if one exists and replays instead of re-executing. Receipts purged only by the retention role after `purge_after` (TB-06). Bulk commit/import confirm use outcome records (§3.6, §3.7) |
| Unknown outcome | `GET /api/v1/operations/{idempotencyKey}` (own keys) re-runs current read authorization on the receipt scope and every represented Matter (as for replay) → `200 {status: COMMITTED, response, asOf}`; key past retention → `410 idempotency-key-expired` (reconcile via `GET /matters/{m}/events?commandKey=`); otherwise uniform `404`, meaning only *no committed outcome visible to you as of `asOf`* — **not** "never committed" (it may be in flight, or access lost). Safe action: resubmit with the **same** key (replays, or executes at most once while the key passes the age check). **No final-absence guarantee:** a 404 never means the original will not commit later, because a DB transaction deadline starts at admission and cannot bound network delay, pre-admission queuing or a delayed first arrival; duplicate-effect safety comes from the receipt PK, scope lock and key-age check, not from elapsed time |
| Provenance | Every response includes `asOf` (RFC 3339 with offset; server-captured database-clock instant — snapshot start for reads, `t_cmd` for commands, state-machine §6.1; a client `asOf` on current-state views → 422), `sourceRevision` (matter event sequence visible to the response), `historyMaterializedThrough` and, for commands, `eventSeqs[]` |
| Time input | Instants must include an offset; date-only input requires `timezone` and is resolved server-side; ambiguous/nonexistent local times rejected (AC-152) |
| Derived fields | Read-only; any attempt to send `dependencyState`, `verificationState`, `timingState`, `attentionState` → `422` |
| Pagination | Keyset (`after`, `limit` ≤ 200 default 100) |
| Errors | RFC 9457 `application/problem+json` (template `toProblem`) with `type` URIs below |

### 3.3 Evidence submission with claims

```json
POST /api/v1/matters/{m}/evidence   Idempotency-Key: …   (If-Match on subject not required: submission does not change subject state)
{ "kind": "DOCUMENT_VERSION", "documentVersionId": "v2", "description": "Signed SPA",
  "validFrom": null, "validUntil": "2026-12-31T23:59:59+07:00",
  "claims": [ { "criterionRevisionId": "cr-5", "componentKey": "signature-party-a" },
              { "criterionRevisionId": "cr-9" } ] }
→ 201 { "evidence": {…, "submittedBy": "U1"}, "claims": [{"id":"k1", "status":"PENDING_REVIEW"}, {"id":"k2",…}] }
```

Evidence submission has CAS scope *none* (§1.1): it creates records and changes no revisioned target; each claim's `criterionRevisionId` must be current. It still requires Idempotency-Key.

### 3.4 Assessment

```json
POST /api/v1/evidence-claims/k1/assessments   If-Match: "<claim revision>"   Idempotency-Key: …
{ "verdict": "ACCEPTED", "rationale": "Signature block complete on page 41",
  "criterionRevisionId": "cr-5", "assessedDocumentVersionId": "v2", "effectiveUntil": null,
  "expectedSubjectEpoch": 0 }
→ 201 { "assessment": {…, "reviewer": "U2"}, "subject": { "verification": "PARTIALLY_VERIFIED", … },
        "derivedChanges": [ … downstream READY … ] }
→ 403 /problems/self-verification | /problems/verifier-not-designated
→ 412 /problems/stale-criterion-revision | /problems/stale-revision (claim revision or subject epoch moved)
→ 409 /problems/guard-failed (open dispute on current assessment)
```
