## 2. Decisions

All three gaps are real. The common pattern is:
- a single point lookup for any ref the client must resolve on its own;
- the label carried in the same snapshot wherever the server emits the ref for display.

Generic `{kind, id}` refs stay unchanged, and no 25-kind resolver is claimed.

Synthetic counterexample, used for both party and workstream: a Matter has 201 records ordered by label, and the referenced record is #201. At the per-page cap of 200 it sits on page 2. This makes no claim about real-world frequency.

### RC-REF-01 — EXTERNAL_PARTY (DR-13)

**Gap**
- DR-13 has only a paginated list with no id filter.
- `waits?partyId=` filters waits, not the party record.
- Refs carry no label. Resolving the counterexample's party #201 would need a sequential page scan.
- My earlier YAGNI rejection of the point route does not survive the counterexample.

**Resolution**
1. Reinstate `GET /api/v1/external-parties/{id}` (REVIEWED_CANDIDATE). It returns exactly the reviewed fields: label, role/context, inactive and revision, plus asOf/sourceRevision. No contact or legal fields.
2. Guaranteed label context, all CANDIDATE_FIELD:
   - `partyLabel` on waitingOn cards and on DR-16 waits;
   - `authorityPartyLabel` on DR-12 filings.

   The overview therefore renders party names without any follow-up reads that would mix snapshots.

**Collection and negatives**
- The list is unchanged and paginated, with no cap assumed; a picker pages through it via cursor.
- Inactive parties stay resolvable for history.
- Nonexistent, foreign, revoked and kind-mismatched ids all return the uniform 404.

**Affected:** DR-13/16/12, NAV-08, CT-03/04/05/09/10/16.

### RC-REF-02 — EVIDENCE_CLAIM (DR-08/09)

**Gap**
- Claims are returned only inline under `GET /evidence/{evidenceId}`.
- `GET /evidence-claims/{claimId}/assessments` returns history only.
- A claim ref arriving from an event, dispute or assessment has no evidenceId to follow.
- This is missing consumer navigation context, not a corrupt stored claim. The only existing safe path is the DR-07 claims summary, which already pairs `claimRef` with `evidenceRef`.

**Resolution (no new route)**
1. Extend the existing `GET /api/v1/evidence-claims/{id}/assessments` response to always include `claim: {claimRef, evidenceRef, criterionRevisionRef, componentKey|null, status, revision}` (CANDIDATE_FIELD) alongside `assessments[]`, which may be empty.
2. The parent is guaranteed: every claim has exactly one Evidence parent and one criterion revision (candidate api-contracts §1.1, §3.3).
3. Consumer path: `claimRef` → claim-assessments route → `claim.evidenceRef` → `GET /evidence/{evidenceId}`. A claimId is never sent to `/evidence/{id}`; if it were, the server returns 404 under RC-3.
4. The `claim` envelope is present on every page of the keyset-paged assessments collection, including continuation pages.
5. **Dispute and revocation contexts.** Candidate commands address assessments and disputes by their own ids (`POST /evidence-assessments/{id}:revoke`, `/disputes`, `POST /disputes/{id}:resolve`), and event target kinds are unspecified. So wherever an ASSESSMENT or DISPUTE ref is emitted (a DR-15 event `targetRef`, a recentChanges card), a sibling `claimRef` (CANDIDATE_FIELD) is carried. The consumer then follows the claim path above. No new route and no resolver for those kinds.

**Semantics**
- A claim with zero assessments returns the claim plus `assessments: []` (it exists but has not been reviewed), which is different from 404.
- Exact `assessedDocumentVersionRef` and `criterionRevisionRef` identity is kept.
- The verification aggregate stays a separate backend projection.

**Affected:** DR-08/09/15, NAV-03/04/10, CT-03/05/10/12/17/19.

### RC-REF-03 — WORKSTREAM (DR-02)

**Gap**
- ≤200 is a per-page cap, not an approved per-Matter count.
- The point route was rejected.
- Neither Requirement/Action refs nor a restored `grid?workstreamId=` URL has a label source without scanning.

**Resolution**
1. Reinstate `GET /api/v1/workstreams/{id}` (REVIEWED_CANDIDATE). It returns label, order and revision, plus asOf/sourceRevision.
2. Add `workstreamLabel` (CANDIDATE_FIELD) next to `workstreamRef` on DR-04 Requirement and DR-05 Action detail. Any shape that later emits a workstream ref for display must do the same.
3. No unpaginated or bounded-list guarantee and no business cap. Pickers page through the list.
4. The grid row shape is an existing candidate that the reviewed contract never specified. If grid rows display a workstream, they carry `workstreamLabel` under the same rule.

**Affected:** DR-02/04/05, NAV-01/05/06, CT-03/05/16/17.

## 3. Shared semantics

- **Authorization (RC-1/RC-3 unchanged):**
  - check order is 401, then server-side owning-Matter resolution, then active Workspace AND explicit Matter membership AND O/E/V role;
  - otherwise a uniform 404 that is byte-identical to nonexistent;
  - a kind mismatch also returns 404;
  - no 403 on P0 reads, no Workspace OWNER implicit grant, no shared-token fallback.
- **Snapshot:**
  - each point lookup is its own boundary and never patches the overview;
  - embedded labels come from the overview snapshot;
  - a newer `sourceRevision` gets "changed since overview";
  - there is no section refetch.
- **Revocation:** purge the protected client cache for that Matter, never domain Event History.

## 4. Consumer acceptance (Antigravity; not results)

1. Clicking a party ref makes exactly one point request, with no list scan. Overview wait cards show party labels with no follow-up request.
2. A standalone claim ref resolves claim and parent evidence in at most two requests, with no guessed ids. So does a dispute or assessment-revocation event in recentChanges, via its sibling `claimRef`. A zero-assessment claim renders as an existing claim that has not been reviewed.
3. Requirement and Action drawers show the workstream label without an extra request. A restored workstream filter resolves its label in one request.
4. The synthetic record #201 (party and workstream) resolves in one request.
5. A revoked member sees the same "not available" state as for a nonexistent record. Cached detail for that Matter is purged.
