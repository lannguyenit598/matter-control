## F01 — P1: withdrawal/revocation silently removes an unresolved dispute from the derived state

- **Trigger:** independently accept proof for a mandatory criterion, raise a dispute, then let the submitter withdraw that evidence (or a designated independent reviewer revoke the acceptance) without resolving the dispute. With another mandatory criterion still accepted, the subject becomes PARTIALLY_VERIFIED; with only this criterion, UNVERIFIED. The dispute remains open.
- **Source:** frozen `apps/backend/internal/core/domain/matter/evidence.go:381–400` returns before scanning disputes when evidence is withdrawn or the assessment revoked. Aggregate evaluation at `267–313` depends on the resulting `ClaimStatus.Disputed`. The command is reachable through `evidence_service.go:873–911` and `1105–1137`; the checklist separately still exposes the open dispute at `485–492`.
- **Impact / requirement:** the subject and W5 disputed-proof gap no longer say DISPUTED while the challenge is unresolved. This contradicts RULE-007, AC-157 (`acceptance-criteria.md:523–530`) and the approved DISPUTED transition/precedence in `state-semantics.md`.
- **Minimum correction:** compute the applicable current-epoch open-dispute flag before validity/withdrawal/revocation returns, retaining its aggregation precedence until an authorized resolution. Withdrawal/revocation must still end satisfaction and keep history.
- **Future validation — NOT_RUN:** shared memory/PostgreSQL contract plus domain case: accepted → disputed → withdraw, and accepted → disputed → revoke. Assert DISPUTED, non-satisfaction, open dispute visible and dependents blocked; resolution then recomputes partial/unverified from remaining proof. Existing `evidence_test.go:198–225` revokes only together with resolution; `contract_w3.go:260–295` resolves before revocation, so neither covers this ordering.

## F02 — P1: a stale proof review can supersede an intervening verdict in the same epoch

- **Trigger:** two independent verifier screens read the same claim/epoch. Reviewer A records REJECTED. Reviewer B's older screen then records ACCEPTED with the unchanged subject epoch and exact evidence version. Both requests succeed; B supersedes A even though B never observed that verdict. A lost-response resend of the same assessment can also append another assessment/supersession.
- **Source:** `apps/backend/internal/core/port/evidence.go:164–176` supplies only the subject-epoch fence; no expected current assessment/generation is carried. `evidence_handlers.go:417–432` explicitly refuses If-Match. `evidence_service.go:1008–1013` checks criterion/epoch, then `1037–1063` loads and blindly supersedes whatever verdict is current at commit. The frontend at `features/proof/actions.ts:179–186` and `repository.ts:118–123` carries no read revision either. A matter lock serializes the writes but does not detect the stale human decision.
- **Impact / requirement:** an intervening rejection can be reversed by a stale review, allowing VERIFIED and dependent readiness again. RULE-018 requires the current revision and rejects stale changes without overwrite; AC-139/160 require stale-state no mutation. The implementation contract's CAS=none assessment row is the source of this mismatch, not approval to change those business semantics. This is distinct from fixed CW1 ETag mapping.
- **Minimum correction:** bind assessment intent to the current assessment ID/generation (including an explicit empty generation for a first review), check it under the matter lock and expose the corresponding stale-conflict result through the existing FE recovery. Align service/HTTP/FE contract together; no automatic resend of this nonreceipted command.
- **Future validation — NOT_RUN:** two-read case within one epoch: A changes verdict, B submits its old generation, B is rejected with no assessment/event/supersession. Freshly read B may explicitly reverse with rationale. Add API and FE contract cases; current `contract_w3.go:208–307` exercises wrong epoch and sequential review, while `evidence_server_test.go:68–85` sends no revision.

## F03 — P1: proofRequired=false lets an editor bypass all package/signature applicability checks

- **Trigger:** an EDITOR creates a filing with `proofRequired=false`, gives it an owner, advances Package Preparation → Signature using an identified version/reference, then Submission using a reference/version. There is no declared package/signature criterion, accepted proof or OWNER no-signature applicability decision. The submission is recorded and the stage advances.
- **Source:** `apps/backend/internal/core/service/filing_service.go:155–187` allows the editor-selected flag. In `domain/matter/filing.go:343–352` declaration checks run only for proof-required filings; `230–233` returns no unsatisfied package criteria for every other filing, and `364–386` accepts submission. `evidence_service.go:424–431` also prevents creating criteria on that filing. `contract_w4.go:23–39` constructs precisely this editor-owned no-proof path; the no-proof happy path and separate OWNER retirement case at `323–375` do not require an applicability decision for the former.
- **Impact / requirement:** a choice about the independent verification axis becomes a blanket waiver of filing package/signature guards. RULE-012 and the approved filing table require applicable package criteria; `state-semantics.md` explicitly requires an OWNER applicability reason before Signature→Submission when signatures do not apply. AC-145/160 require missing-signature rejection and guarded no-signature variants. This finding does **not** require giving every no-proof Filing a verification state.
- **Minimum correction:** enforce package/signature applicability and completeness independently of the filing's outcome-verification flag. Keep the supported no-proof axis; require the explicit OWNER no-signature decision instead of inferring it from an editor's creation flag. Align the local contract/fixtures to the approved separation.
- **Future validation — NOT_RUN:** editor-created no-proof filing with no applicable package/signature decision cannot submit, produces no submission/event/revision; explicitly authorized no-signature applicability can proceed with its retained rationale. Cover both storage contracts and HTTP; retain successful no-proof approval tests after legitimate prerequisites.

## F04 — P2: the Control Room page presents facts from multiple snapshots as one boundary

- **Trigger:** another editor renames a linked work item, closes a decision or adds context while the page's parallel requests are in flight. `/control-room` can return revision n, while `/work-items` or `/context-records` returns n+1. All requests may succeed and the page renders the mixture without a stale indicator or revision comparison.
- **Source:** `apps/frontend/src/app/(app)/matters/[matterId]/control-room/page.tsx:34–55` independently loads matter, members, parties, work rows, context and room; it derives display labels from the separate work list and renders the separate context records at `69–109`. `features/control/components/control-room-view.tsx:88–91` claims every figure belongs to the room boundary, but linked record labels (`145–147`, `198–202`, `218–241`) come from that other read. `features/control/repository.ts:11–20` exposes no shared snapshot binding. In contrast the BE `control_service.go` and `work_service.go:945–979` intentionally build the room inside one authorized snapshot.
- **Impact / requirement:** a decision can simultaneously appear open in the room and closed in the page's context area, or causal links can carry names inconsistent with the advertised as-of. AC-109/156 (FR-009) require matching authorized facts at that boundary and distinguish stale data. Independent request success is insufficient evidence of consistency.
- **Minimum correction:** use room-snapshot facts for its displayed context/causal labels, including needed display labels in that same authorized read where absent. Alternatively detect mismatched revision boundaries and withhold/label the inconsistent sections; do not silently combine them as one snapshot. Any separately current edit panel must identify its own boundary.
- **Future validation — NOT_RUN:** page orchestration test with deliberately different room/work/context revisions and a concurrent decision closure; assert one coherent boundary or explicit stale handling. Current `control-ui.test.tsx:50–164` renders one handcrafted room/label pair and never calls the page's parallel reads; `control_server_test.go:43–64` verifies only one backend response.
